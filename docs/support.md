# Suporte e distribuição

O código exige Go 1.26 ou mais recente. A escolha acompanha os dois releases principais mantidos pelo projeto Go; confirme a versão mínima antes de cada release. O workflow CI declara teste e build em Linux, macOS e Windows `amd64`; resultados verdes precisam ser confirmados no CI antes de uma release. `arm64` ainda precisa ser verificado antes de anunciar suporte. Consulte a [política oficial de suporte do Go](https://go.dev/doc/devel/release#policy).

O scan padrão usa regras locais e o cache SQLite de inteligência; não acessa a rede. Gitleaks 8.16.0 foi testado como engine opcional: `mitnick scan --gitleaks` executa-o somente após opt-in, sobre uma cópia temporária dos arquivos descobertos, sem rede e com limite de 30 segundos. Em Linux/macOS, diretório e arquivos temporários usam modos `0700`/`0600`; no Windows, herdam a ACL do diretório temporário, que deve ser privado. A cópia e o relatório temporário são removidos ao terminar normalmente; encerramento abrupto pode deixar a cópia no diretório temporário e não há garantia de apagamento físico. O processo usa a conta atual e não recebe isolamento por sandbox do sistema operacional; instale e confie no binário usado. `mitnick intel update` integra diretamente a API OSV sem executar ferramentas do projeto. O executável externo `osv-scanner` é detectado por `doctor`, mas não é integrado. Nenhuma engine é baixada nem atualizada pelo Mitnick.

`mitnick menu` usa Bubble Tea e navegação por teclado, sem depender do mouse. A compatibilidade real com combinações de terminais, resize, cores e execução Windows/macOS ainda precisa passar pela matriz CI antes de anunciar suporte. `mitnick ai detect/list` só consulta o `PATH`; `ai connect` executa o status de login do CLI selecionado e salva a escolha. A revisão consultiva suporta Codex CLI e Claude Code autenticados localmente, em modos não interativos com ferramentas do modelo desativadas e contexto sanitizado enviado por stdin. Verifique versão do CLI, políticas da conta/organização e custos antes de usar; o Mitnick não verifica roteamento nem limite de consumo. Os testes automatizados usam CLIs simulados, sem login ou chamadas a serviços reais.

## Arquivos de agentes reconhecidos

A inspeção é textual e não interpreta todas as variações de cada cliente:

- Instruções: `AGENTS.md`, `CLAUDE.md`, `CLAUDE.local.md`, `.cursorrules`, `.windsurfrules`, `.clinerules`, `copilot-instructions.md`, `gemini.md` e arquivos `*.instructions.md`.
- Configurações MCP dentro da pasta analisada: `.mcp.json`, `mcp.json`, `mcp_config.json`, `mcp-config.json`, `claude_desktop_config.json`, `.gemini/settings.json`, `gemini-extension.json` e arquivos `.json` dentro de um diretório `mcp/`. Os formatos de VS Code (`.vscode/mcp.json`), Cursor (`.cursor/mcp.json`) e Copilot/Gemini são reconhecidos por esses nomes; configurações globais fora do alvo do scan não são descobertas. Referências consultadas em 25/10/2026: [VS Code](https://code.visualstudio.com/docs/agents/reference/mcp-configuration), [Cursor](https://docs.cursor.com/context/model-context-protocol) e [Gemini CLI](https://google-gemini.github.io/gemini-cli/docs/get-started/configuration.html).

Só comandos, argumentos e caminhos com padrões conhecidos são sinalizados. Outras estruturas, permissões efetivas e comportamento do servidor não são avaliados.

Para gerar pacotes reprodutíveis, SBOM SPDX 2.3 e checksums locais em um ambiente Linux com GNU tar, gzip, Python 3 e `sha256sum`, execute `bash scripts/package-release.sh v0.1.0 /caminho/de/saida`. O SBOM é extraído dos metadados de build de cada binário; licenças não são inferidas e aparecem como `NOASSERTION` até revisão. O timestamp usa `SOURCE_DATE_EPOCH` (padrão `0`) para manter a saída repetível. `.github/workflows/release.yml` prepara a publicação por tag, valida os checksums e solicita atestação SLSA dos pacotes; o workflow ainda não foi executado e nenhum artefato está publicado. A atestação liga a proveniência aos hashes dos pacotes; ela não substitui a verificação de checksum nem constitui assinatura offline do executável. O serviço de atestações exige repositório público em planos comuns do GitHub ou Enterprise Cloud para repositórios privados ([requisitos do GitHub Attest](https://github.com/actions/attest)). Após uma release pública, um GitHub CLI recente pode validar a proveniência com [`gh attestation verify`](https://cli.github.com/manual/gh_attestation_verify): `gh attestation verify <pacote> --repo <proprietário>/<repositório>`.

Antes de uma publicação pública: concluir a revisão jurídica das licenças de código e dados (o inventário inicial está em `THIRD_PARTY_NOTICES.md`), validar disponibilidade/marca do nome, confirmar matriz CI, revisar a cadeia de build, decidir assinatura dos checksums e configurar um canal privado de segurança.
